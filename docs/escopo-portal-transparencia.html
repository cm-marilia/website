Escopo de melhorias do Portal de Transparência

Nove páginas HTML no GitHub Pages, embutidas em marilia.sp.leg.br, lendo planilhas do Google Sheets publicadas como CSV. Este documento reúne as decisões em aberto e as correções propostas, para revisão antes de qualquer implementação.

Revisão: 28/08/2026 Status: aguardando decisão Nada implementado até aqui

Como funciona hoje

Cada página (contratos.html, servidores.html, diarias.html, remuneracao_detalhada_servidores.html, estagiarios.html, empresas_sancionadas.html, painel_orcamentario.html, painel_manifestacoes.html, julgamentos_contas_camara.html) baixa um CSV publicado do Google Sheets, monta cards/tabelas no navegador e envia a altura ao site pai via postMessage. O selo verde de "dados atualizados em…" vem de uma célula MODIF_REAL: dd/mm/aaaa, hh:mm na primeira linha da planilha.

O portal funciona. As melhorias abaixo tratam de fragilidade, falha silenciosa e manutenção — não de defeito ativo.

Decisões em aberto

Três escolhas dependem de você. As demais melhorias (seção seguinte) não exigem decisão — só priorização.

Decisão 1

Fonte dos dados: manter CSV publicado ou migrar?

Hoje as páginas leem o link /pub?output=csv do Google Sheets. Isso exporta o valor exibido na planilha (data como 10/01/2023, número como 2026) — e é por isso que funciona, apesar de algumas células de identificador estarem armazenadas internamente como data.

OpçãoGanhoCusto
Manter CSV publicadoZero mudança. Já em produção.Atraso de propagação (~minutos). Depende da formatação de exibição da planilha. Expõe toda aba publicada.
Web App (Apps Script) devolvendo JSONData real de modificação do arquivo; formatação de datas/números controlada no servidor (resolve o problema dos IDs); sem atraso; controle de CORS.Adaptar o carregamento das 9 páginas (CSV → JSON). Esforço médio.
CSV versionado no repositório (ver Decisão 3)Histórico dos dados; independência do Google em tempo real.Requer automação. Ver Decisão 3.
Recomendação: manter o CSV publicado por ora, e aplicar a correção de origem A1 (formatar colunas de identificador como texto). Reavaliar o Web App JSON quando for mexer no parser de datas de qualquer forma — os dois trabalhos se sobrepõem.
Decisão 2

Carimbo de "última atualização": como alimentar?

Hoje alguém digita MODIF_REAL: … na célula A1. Alternativas:

OpçãoComportamentoObservação
1. Apps Script preenche A1 (gatilho onChange)Grava o timestamp a cada edição da planilha. Nenhuma mudança nos HTML.Qualquer edição atualiza o carimbo — inclusive correção de digitação.
2. Web App expõe getLastUpdated()Data real do arquivo no Drive, sem "linha mágica".Só faz sentido junto da Decisão 1 (migração para JSON).
3. Timestamp da automação (meta.json)Hora da última sincronização registrada pelo processo.Só faz sentido junto da Decisão 3.
Definir o significado "Planilha foi tocada em X" (opções 1 e 2) é diferente de "os dados estão corretos até X" (afirmação humana). Escolher a opção depende de qual dos dois o selo deve comunicar ao cidadão.
Recomendação: Opção 1 agora — rápida, sem risco, sem tocar nos HTML. Migrar para a Opção 2 se a Decisão 1 for pela migração.
Decisão 3

Automatizar a sincronização dos dados?

Trazer os CSVs para o repositório (versionados) elimina o atraso do Google, cria histórico e reduz o acoplamento com a disponibilidade do Sheets em tempo real. Duas formas:

OpçãoCusto financeiroPrós / contras
GitHub Actions (cron baixa e comita)Gratuito para repositório público (minutos ilimitados).+ histórico, resiliência.
− cron impreciso (atraso 5–20 min); workflow agendado desativa após 60 dias sem atividade no repo; mais uma peça a manter.
Apps Script push (planilha escreve no repo via API do GitHub)Gratuito.+ event-driven (atualiza no instante da mudança); lógica concentrada na planilha; não desativa sozinho.
− exige token do GitHub guardado no Apps Script.
Não automatizar—Mantém a simplicidade atual. Convive com o atraso e a exposição da planilha.
Recomendação: não é prioridade. Se for fazer, o Apps Script push tende a ser mais simples para um portal mantido essencialmente por uma pessoa — sem cron, sem workflow, menos conceitos novos. Automação é "bom ter", não "crítico".

Ordem sugerida de execução

  1. A1 — formatar as colunas de identificador como texto. Cerca de 10 minutos; protege a versão atual de imediato.
  2. B1 + B2 + B3 — parser de data tolerante, guard pós-carga e try/catch. Elimina as falhas silenciosas.
  3. A2 + A4 — padronizar a linha 1 e revisar o que cada planilha publicada expõe.
  4. B4 + B5 — auditoria de segurança das 9 páginas e SRI nas libs.
  5. B8 — acessibilidade (e-MAG).
  6. Decisão 3, se aprovada — automação da sincronização. Maior ganho de longo prazo, menor urgência.

Riscos conhecidos (sem ação imediata)

  • Dependência de uma pessoa. Documentar o processo de manutenção reduz o risco de "só uma pessoa sabe".
  • Google Sheets "publicar na web" já foi descontinuado uma vez pelo Google no passado; a Decisão 3 mitiga.
  • 4 CDNs distintos (jQuery, DataTables, SheetJS, PapaParse) — cada um é um ponto único de falha até o item B5.
  • LGPD: auditoria atual não encontrou CPF desprotegido. Manter a verificação a cada nova página ou coluna.
